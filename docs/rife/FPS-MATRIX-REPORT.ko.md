# Framegen 추가 FPS 검증

Framegen 1.4.0 / 원본 v7-small 가중치를 그대로 사용한 **독립 하네스** 결과입니다. 새 보간 엔진을 만들거나 제품 스케줄러를 교체하지 않았습니다. 기존 720p60→90 기록은 [기존 원시 자료](../v1.3/framegen/benchmark.json)에 보존했습니다. 이 보고서는 제품·YouTube·청각적 동기화 완료 보고가 아닙니다.

환경: Windows / headless Chromium 156.0.8078.4. 하드웨어 WebGPU adapter는 nvidia / lovelace, shader-f16 사용입니다. 특정 컴퓨터의 합성 입력 결과이며 다른 GPU에서 같은 성능을 보장하지 않습니다.

원시 JSON의 canvasNearTarget은 목표의 98%에 근접했는지만 표시하는 진단값이며, 합격 기준으로 사용하지 않았습니다. 특히 누락·지연이 있는 60→90을 안정 유지 성공으로 판정하지 않습니다. AI 호출은 실제 prepPair/runT 실행 경로입니다. 별도 GPU 진단이 **모든 native RGB 픽셀**을 원본 A/C와 비교하므로 단순 원본 복사를 생성으로 세는지 확인할 수 있습니다. 그러나 RGB가 다르다는 사실은 정확한 보간의 증명이 아닙니다. 정확도는 아래 숨겨둔 B로 따로 평가합니다.

고유 수는 전체 native RGB의 64-bit GPU 지문입니다. 해시 충돌 가능성이 있어 수학적으로 완전한 픽셀 집합 동등성 증명은 아닙니다. 전체 고유 수는 움직임의 반복 때문에 제출 수보다 작을 수 있고, 연속 중복은 별도로 기록합니다. **물리 모니터의 고유 표시 수는 측정하지 않았습니다.** 분석 readback은 테스트 전용 3슬롯·32바이트이며 일반 제품 렌더링에는 추가하지 않았습니다. 이번 FPS에는 이 진단 비용도 포함합니다.

AI 호출 수는 원본 FPS의 차이만큼 넣은 이상적인 중간 프레임 수와 다릅니다. 기존 하네스는 디스플레이 시계에 맞춰 연속 시각으로 재표본화하므로 원본 PTS와 어긋난 출력은 매번 AI를 호출합니다. 따라서 24→48의 1,440회는 720개의 원본 보존 + 720개의 중간 삽입을 입증하는 수치가 아닙니다. 원본 직접 제출 수는 제출−AI 호출로 계산할 수 있습니다.

A/C 대기 오프셋은 추론 시간 자체가 아닙니다. 원본 주기는 실제 PTS 간격의 최근 중앙값으로 계산하고 PresentationClock의 예상 표시 시각을 재사용했습니다. 최근 두 쌍과 원본 texture 3개를 유지합니다. 계획 시간은 A/C 범위 안에서 계산하며 역행·동일 PTS는 제출하지 않습니다. 출력 queue는 최대 3입니다. native drop은 브라우저 카운터로 **준비 3초를 포함**하며 모델의 계획 누락과 다릅니다. 지연 완료는 queue 완료 통지가 목표 간격보다 긴 경우이며, 이 하네스가 늦은 GPU 작업을 완료 후 취소하는 제품 정책까지 구현했다는 뜻은 아닙니다.

입력은 자체 생성한 무음 VP8입니다. 오디오 트랙이 없고 muted로 시험했으므로 **실제 음향·립싱크는 검증하지 못했습니다.** PTS 시간차를 오디오 동기화 통과로 해석하지 마세요.

## A/C만 입력한 B 정답 비교

A/C 간격이 요청 원본 FPS의 한 주기이며 B는 목표 출력 시각입니다. A/B/C는 독립적으로 VP8 keyframe 인코딩 후 실제 VideoDecoder로 디코드했고 **B는 모델·벡터·GPU 입력에 전달하지 않았습니다**. t=(PTS_B-PTS_A)/(PTS_C-PTS_A)입니다. 60→90에서는 약 2/3 시점, 나머지는 약 1/2입니다. 같은 저FPS 영상에서 중간 원본을 누락해 원본 FPS의 절반을 평가하는 방법과 구분합니다. legacyAccuracy에는 제어 검사를 추가하기 전 결과를 보존했습니다. 최초 720p24의 strided 참조는 별도 과거 이미지에도 남겨 두었습니다. 자연 촬영·실제 애니메이션 정답 평가는 아닙니다.

## 실패·제약 분석

24→48 및 30→60은 두 해상도 모두 계획 누락 0, 관측된 GPU 완료 지연 0이었습니다. **60→90은 엄격한 안정 유지 검증을 통과하지 못했습니다.** 720p는 계획 누락 6/지연 완료 38, 1080p는 16/1,274입니다. 1080p queue 완료 p95 16.1ms가 90FPS 예산 11.11ms를 초과했습니다. native 원본 누락도 3/4개 관측됐습니다. 이번 작업은 기존 엔진 검증이므로 성능 기준이나 엔진을 바꿔 이를 숨기지 않았습니다.

missed는 queue 포화/사용 가능한 A·C 부재/역행 보류의 합계입니다. rAF가 늦게 호출돼 건너뛴 목표 tick 전체를 세는 카운터가 아니므로 전체 누락 수로 해석하면 안 됩니다. 30초 목표 제출 약 2,700개 대비 실제 2,678/2,653개이며 제출 간격 최대도 36.7/62.7ms입니다. 평균만 근접해도 균일한 출력 간격은 입증되지 않습니다.

진단 없는 기존 720p60→90은 89.998FPS였습니다. 이번 전수 RGB GPU 진단과 비동기 readback에도 비용이 있고, 실제 rVFC 수신률과 rAF도 달라졌습니다. 서로 다른 실행이므로 어느 하나만을 감소의 확정 원인이라고 주장하지 않습니다. 1080p는 더 큰 모델 입력과 진단 작업의 여유가 부족하다는 증거가 있으며, 추후 별도 kernel timestamp/브라우저 trace로 원인을 분리해야 합니다.

A/C 참조 합성 장면에서 전역 및 국소 오차는 기존 Optical Flow보다 개선됐습니다. 컷 제어는 흰색 C를 정확히 선택했고 정지 입력은 최대 2~6 채널 값의 미세 차이가 남았습니다. 이 결과만으로 반복 무늬·실제 애니메이션·실사에서 블록 왜곡/잔상이 해결됐다고 판정하지 않습니다. 기존 [11장면 품질 보고서](QUALITY-REPORT.ko.md)의 악화·잔여 문제도 유효합니다.
